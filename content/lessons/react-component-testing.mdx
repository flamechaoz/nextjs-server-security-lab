## What you'll learn

- Render a component with JSDOM and mocked network responses.
- Query controls by accessible role and name.
- Use userEvent for realistic interactions.
- Assert loading, success, and error states through visible UI.

### Component tests need a realistic boundary

Render the component with the same props and browser-facing dependencies it uses in the app. For a component that calls `fetch`, mock the network boundary and return the responses the component expects. The test should control the response sequence without reaching a real server.

`TaskManager` loads tasks on mount, sends a `PATCH` request when a user completes a task, and loads the tasks again. That means the test needs an initial `GET` response, a successful `PATCH` response, and a final `GET` response showing the updated task.

### Prefer user-visible contracts

React Testing Library encourages queries that resemble how a user or assistive technology finds elements. Prefer `getByRole` with an accessible name for buttons, links, headings, and form controls. Use `findBy...` when the element appears after asynchronous work, and use `waitFor` when waiting for a state transition.

### Avoid brittle implementation tests

Do not depend on private state, incidental class names, DOM nesting, or the implementation's fetch helper. A class can change during a redesign while the user's task remains the same. Query the control by the name a user can perceive and assert the text or state that the user can see.

### Use userEvent for interactions

`userEvent` models browser interactions more closely than calling event handlers directly. Set up a user, find the control by its accessible name, click it, and wait for the resulting UI. Keep `fireEvent` for lower-level cases where a specific event is the behavior under test.

### Test loading, success, and failure

Loading text is useful while a request is pending. A successful response should produce the expected content or status. A failed response should produce an accessible, user-visible error. Test the state that matters to the user instead of asserting only that `fetch` was called.

### Code walkthrough: a complete TaskManager test

```tsx
import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import TaskManager from "@/components/TaskManager";

it("completes a task through the user-facing control", async () => {
  const task = {
    id: 1,
    title: "Write an accessible test",
    completed: false,
    ownerId: "demo-user",
  };
  const completedTask = { ...task, completed: true };

  // Arrange: control the component's three network responses.
  const jsonResponse = (body: unknown, status: number) => ({
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  }) as Response;
  const fetchMock = jest.fn()
    .mockResolvedValueOnce(
      jsonResponse({ data: [task], count: 1 }, 200),
    )
    .mockResolvedValueOnce(jsonResponse(null, 204))
    .mockResolvedValueOnce(
      jsonResponse({ data: [completedTask], count: 1 }, 200),
    );
  Object.defineProperty(globalThis, "fetch", {
    configurable: true,
    value: fetchMock,
    writable: true,
  });
  const user = userEvent.setup();

  // Act: render, wait for loading to finish, and perform the user action.
  render(<TaskManager />);
  await screen.findByText("Write an accessible test");
  await user.click(screen.getByRole("button", { name: "Complete" }));

  // Assert: verify what the user sees and the important request contract.
  await waitFor(() =>
    expect(screen.getByText("Completed")).toBeInTheDocument(),
  );
  expect(fetchMock).toHaveBeenCalledWith("/api/tasks/1", {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ completed: true }),
  });
});
```

The test does not query `.button`, `.primary`, or `.task`. Those classes can change without changing the behavior. The accessible button name and the visible `Completed` status are the stable contract.
