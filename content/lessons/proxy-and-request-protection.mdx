## What you'll learn

- Explain the purpose of Proxy.
- Observe request forwarding, redirects, rewrites, and matcher coverage.
- Pass trusted request context to a handler.
- Keep authorization close to protected data.

### Proxy is an early gate

Proxy runs before matched routes. It can make lightweight request checks, redirect users, rewrite a request to another internal destination, or forward it with request headers. In this lab, the matcher covers `/api/debug/lesson-13` and its nested paths. The playground lets you observe these outcomes without leaving the activity page.

### It is not the whole security model

A cookie-presence check is not authentication: clients can invent cookie values. This lab's Proxy rejects requests with no Module 9 cookie, but accepts a fabricated value. The practice handler also omits session validation, so add that check before returning protected data. Current Next.js versions use proxy.ts; older projects may use middleware.ts.

## Walkthrough

1. Inspect proxy.ts and review the matcher.
2. Use the playground signed out, then sign in through Module 9 and retry.
3. Compare the continue, redirect, and rewrite outcomes.
4. Send a fabricated cookie (for example, `curl -H 'Cookie: next-lab-demo-session=fake' ...`) and observe that Proxy accepts it.
5. Check that the Route Handler validates the session rather than trusting Proxy alone.
5. Avoid putting database-heavy authorization logic in Proxy.
