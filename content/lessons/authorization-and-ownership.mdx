## What you'll learn

- Explain IDOR and broken object-level authorization.
- Distinguish Module 9 authentication (who is signed in) from authorization (what that user may access).
- Check resource ownership on the server.
- Test both allowed and denied access.

### Authentication is not authorization

Module 9's session establishes the authenticated identity. Module 10 uses that same server-verified session to make an access decision for each resource. A valid session does not grant access to every task, and a task ID supplied by the browser is never proof of ownership.

### A valid ID is not permission

Knowing a record ID must not grant access. Every protected read and mutation needs a server-side permission check for the current user and requested resource.

### Check at the data boundary

Middleware can help with coarse routing, but ownership checks belong close to the resource operation as well. Do not rely on hidden buttons or client-side checks.

## Walkthrough

1. Sign in at `/authentication-sessions` to establish the Module 9 demo session.
2. Open `/authorization-and-ownership` and try both task IDs.
3. Trace how the API obtains the user from the shared session cookie.
4. Add an ownership check before returning the task.
5. Test signed-out, owner, different-owner, and missing-resource cases.
